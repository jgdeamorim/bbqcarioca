E eu vejo uma regra arquitetural fundamental surgindo:

Service Request deve ser o objeto central do negócio.

Não Candidate.

Não Payment.

Não Event.

O fluxo é:

Cliente solicita um serviço → BBQ monta preço → gerente aprova → cliente paga → sistema monta equipe → evento acontece → todos avaliam → dados alimentam a próxima operação.

Isso é muito mais coerente com o negócio.

E podemos continuar mantendo o núcleo Cloudflare/D1/R2/Workers; o gateway de pagamento e os canais externos entram como serviços periféricos, sem contaminar o banco com dados financeiros sensíveis.

Para o MVP, eu priorizaria Service Request → Quote → Manager Approval → Payment Link → Event → Feedback, deixando settlement da equipe e integrações avançadas de reviews para a segunda camada.
